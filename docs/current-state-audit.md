# Current-state audit — Phase 0.2

Written before any redesign work, per the overhaul task doc's Phase 0. Baseline
captured on branch `overhaul/publication-redesign`, commit at branch point
`e1bce1c`. Screenshots referenced below are in `docs/baseline-screenshots/`
(28 files: 7 routes × 4 breakpoints — 1440×1000, 1024×768, 768×1024,
390×844). Zero console errors across all 28 baseline captures.

## Framework, build, hosting

- **Framework**: React 18 + TypeScript, via Vite 6. Client-rendered SPA —
  confirmed by hand: `curl http://localhost:5173` returns `<div
  id="root"></div>` with no server-rendered content at all. **With
  JavaScript disabled the page is blank** except the `<title>`/meta tags —
  this directly conflicts with the overhaul doc's Phase 11.3 requirement
  ("must not fail with JavaScript disabled... titles, findings, source
  notes, static chart fallbacks"). No SSR/SSG step exists anywhere in the
  toolchain. Flagged as a real, unresolved architecture decision below.
- **Build**: `npm run build` → `tsc -b && vite build`. Clean as of this
  audit: 0 typecheck errors, build succeeds in ~0.6s.
  - Bundle: `index.js` 429.64 kB (152.72 kB gzip), plus a lazy-loaded
    `countries-50m.json` chunk at 756.54 kB (236.33 kB gzip, only fetched
    when a reader expands the world map). Vite's own build warns these
    exceed its 500 kB chunk-size default.
  - CSS: 12.67 kB (3.47 kB gzip) — small; `src/styles/index.css` is one
    hand-written file, no CSS framework.
- **Tests**: `npm run test` → `vitest run`. **Zero test files exist.**
  Vitest itself is an installed devDependency with no config beyond
  defaults; nothing has ever been written against it in this app's current
  form.
- **Hosting**: static GitHub Pages, deployed by
  `.github/workflows/build-and-deploy.yml` on every push to `main` (no
  cron — see CLAUDE.md's "Ingestion" section for why: nothing behind this
  app's data updates faster than annual). Custom domain
  `www.emersonjohnston.org/talent-monitor/`.
- **Deploy command**: `npm run build` (workflow's own `Build` step) →
  `actions/upload-pages-artifact@v3` → `actions/deploy-pages@v4`.

## Source and data directories

- `src/App.tsx` — single-file app shell: theme, dashboard-tab state, one
  `fetch('data/talent.json')` on mount, one live `fetch` per news-ticker
  feed on mount (`src/lib/sources/rss.ts`).
- `src/dashboards/` — `Overview.tsx` + 6 `Track*.tsx` files (one per
  stage) + a shared `TrackShell.tsx` (renders a stage's hero + a plain
  3-column grid of every other exhibit for that stage) + `types.ts`
  (`DashboardContext`).
- `src/components/` — 15 files. Generic chart primitives: `BarRow`,
  `KpiCard`, `Sparkline`, `SeriesChart` (hand-rolled SVG line/area),
  `WorldMap` (`react-simple-maps` + `d3-geo`), `LeaderboardYears`,
  `Leaderboard`, `Sankey` (hand-rolled + `d3-sankey`,
  `SankeyParticleDots`), `Tooltip`, `ChartFrame` (`SectionHeader`,
  `PolicyTakeaway`, `ExpandableMethods`), `NewsTicker`,
  `DashboardNavigation`. `ExhibitChart.tsx`/`ExhibitPanel.tsx` are the
  dispatch layer: one `Exhibit` → whichever chart its `kind` maps to.
- `src/lib/` — `types.ts` (the `Exhibit`/`Stage`/`DataFile` data
  contract), `exhibitData.ts` (generic extraction helpers), `sankeyData.ts`
  (the two Sankeys' real data prep), `countries.ts`/`continentMap.ts`
  (ISO country name/color), `newsFeeds.ts` + `sources/rss.ts` (live news),
  `stageColor.ts`, `urlState.ts`, `useCountUp.ts`/`useReducedMotion.ts`.
- **Data**: `public/data/talent.json` — one committed static file, 86 real
  exhibits, regenerated by `scripts/import-talent-charts.ts` from
  `talent_charts/` (the report's own R project, absorbed into this repo as
  plain files) whenever that source changes. No raw/processed/metadata
  split — the importer reads `talent_charts/data/*.csv` +
  `titles_and_sources.csv` directly and writes one flat `Exhibit[]`.
  `data/talent/notes.ts` holds the 6 hand-written analyst notes (one per
  stage).
- **No CSV/JSON per-chart download exists.** A reader cannot currently
  export any chart's underlying data (`csvExport.ts` existed in an earlier
  version of this app and was deleted as unused before this data model
  existed — see git history).

## Chart library strategy (real finding, not yet decided)

**No declarative chart library is used anywhere.** Every chart in this app
is hand-rolled SVG:
- `SeriesChart.tsx` — manual `M`/`L` path strings, manual axis-tick/
  gridline placement, manual hover-crosshair math.
- `BarRow.tsx` — a plain flex/width-percentage bar, no SVG.
- `WorldMap.tsx` — `react-simple-maps` (a thin `d3-geo` wrapper) for
  projection math only; fill colors, ticks, tooltip, and the
  particle-free/expand-to-fullscreen behavior are hand-rolled.
- `Sankey.tsx` — `d3-sankey` for node/link layout only; every visual
  element (ribbons, particle animation, hover/pin, labels) is hand-rolled
  SVG + a hand-rolled particle-motion technique
  (`sankeyParticles.ts`/`SankeyParticleDots.tsx`, SVG SMIL `animateMotion`).

This has held up fine at the current "one chart, one panel" density, but
the overhaul doc's Phase 4.3 explicitly asks for a declarative library for
standard forms (line/area/bar/dot/scatter/heatmap) and reserves
hand-rolled/D3 for Sankeys and other custom flows. **Adopting one is a
real, repo-wide decision** — every existing chart component would either
be rewritten on top of the new library or explicitly kept hand-rolled with
a documented reason. Flagged for your decision before Phase 3/4 begin; see
the message accompanying this audit.

## Routing and URL state

- One query param: `?dashboard=<stage-id>` (`src/lib/urlState.ts`). Browser
  back/forward restores it (`popstate` listener in `App.tsx`).
- **No country filter, no compare mode, no year/range selection, no map
  selection, no series-search state exists in the URL or anywhere else.**
  The only cross-panel interactive state is an in-memory (non-URL)
  "emphasize this country" hover broadcast, reset on every navigation.
- No per-stage sub-routes (`/foundation/`-style paths) — everything is one
  route (`/`) with a query param. `vite.config.ts`'s `base` is set via
  `GTM_BASE` env at build time for the GitHub Pages subpath.

## Typography and color tokens

- Tokens live in `src/styles/index.css`'s `:root` block: `--red` (Hoover
  red `#98002e`, the one accent), `--country-us/-cn/-in/-eu/-other` (named
  country identity), `--cont-na/-sa/-eu/-as/-af/-oc/-me` (7-color
  categorical palette, repurposed for non-country chart series), one
  neutral ink/panel/line scale, light + dark theme variants.
- **No warm neutral (`#887E6F`), light gray (`#A7A9AC`), or dark gray
  (`#777575`) tokens exist** — the overhaul doc's supplied palette hasn't
  been introduced yet.
- Font: `Inter` (system font stack fallback), loaded via... **not
  confirmed in this audit** — no `<link>` to a font host is in
  `index.html`, so `Inter` is likely resolving to the OS-installed variant
  where present, an unstyled system fallback where not. Needs a real check
  before Phase 3 (self-hosted vs. approved web font, per the doc's "do not
  add local font files without approval" rule).
- One type ramp (`--fs-hero` through `--fs-methods`), no separate scale for
  publication title vs. stage title vs. finding headline vs. chart title —
  most headings currently share `.panel h3`'s single 16px/700 rule.

## Existing UX/interaction inventory

- Hover tooltips on every chart type (bars, lines, map, Sankey).
- Click-to-pin on Sankey nodes/links (persists after mouse leaves).
- Cross-highlight: hover a country on one exhibit's map, matching country
  series dim/brighten on every other exhibit on the same page (added last
  session, real and working — see `TrackShell.tsx`'s shared
  `emphasizeCountry` state).
- `ExpandableMethods` (collapsed-by-default citation) on every panel.
- `prefers-reduced-motion` respected for the Sankey particles, KPI
  count-up, and page-tab mount transition (`useReducedMotion.ts`).
- **No keyboard-specific chart interaction exists** beyond default
  tab-focusable buttons/links — no arrow-key series stepping, no
  keyboard-reachable map country selection (map countries are
  `tabIndex={0}` + `Enter`/`Space` only when `onSelect` is passed, which
  currently nothing does — country-map exhibits have no click behavior at
  all today, only hover).
- **No accessible chart-summary text** (screen-reader alt content) exists
  for any SVG chart — `aria-label`s exist on the outer `<svg>` (e.g.
  `WorldMap`'s "World map, shaded by real per-country value...") but
  convey the chart's topic, not its actual values.

## Existing report-to-web mapping

**None exists as a structured artifact.** `scripts/import-talent-charts.ts`
maps each of the report's 86 final exhibits (`FIG1xx`–`TAB6xx`) to a
`{stage, chapter, order, kind}` tuple and every exhibit renders somewhere
(`TrackShell.tsx`'s "every exhibit shows up, no top-N cut" rule) — but there
is no per-figure disposition (`stage_hero` / `supporting_visual` /
`integrated_into_other_visual` / etc.), no record of *why* a given chart
form was picked, and no tracking of the 6 report exhibits that were never
ported (`TAB303`, `FIG405`, `TAB503`, `TAB504`, `TAB603`, `TAB605` — logged
by the importer at import time, not in a durable file) or the 77
archived/cut exhibits (`AF`/`AT`-prefixed) that were never imported at all.
Building the crosswalk this doc's Phase 1 asks for starts from zero, not
from a partial existing file.

## Code to reuse vs. replace (my assessment)

**Reuse as-is or with light adaptation:**
- The entire data layer: `Exhibit`/`Stage`/`DataFile` model,
  `scripts/import-talent-charts.ts`, `exhibitData.ts`'s extraction
  helpers, `public/data/talent.json` itself. This is real, correctly
  cited, already-validated data — nothing about the redesign should touch
  how it's sourced.
- `countries.ts`/`continentMap.ts` (ISO country handling).
- `sankeyData.ts`'s two real data-prep functions (the numbers are right;
  only the presentation/interaction around them needs work).
- The live news pipeline (`newsFeeds.ts`, `sources/rss.ts`, the Worker) —
  functionally sound, just needs the ticker's own UI treatment revisited
  per Phase 2.4.

**Replace or substantially rework:**
- `TrackShell.tsx`'s "one hero + undifferentiated 3-column grid of
  everything else" layout — this is exactly the "card wall" the doc's
  non-negotiable rules prohibit. Confirmed visually:
  `docs/baseline-screenshots/research-output__desktop-1440x1000.png` shows
  19 same-weight panels, several with illegible 5-11-series micro-legends,
  one with a known-bad generic-fallback label collision ("colt"/"corl" —
  `TAB501`, the AI-conference dataset, has no bespoke chart yet, so it
  falls through to the generic ranked-bar renderer and produces
  near-meaningless labels at this data shape).
- `SeriesChart.tsx` for any chart with more than ~6 series — no
  series-picker exists; everything currently renders as one line per
  column, unreadable past 6 (Phase 4.5's own threshold), several current
  exhibits have 10-19 series (e.g. `FIG206`, `FIG509`+critical-tech
  patent panels).
- `DashboardNavigation.tsx` — a flat button row of 7 labels; already wraps
  to 3+ rows on mobile (see `docs/baseline-screenshots/*__mobile-390x844.png`),
  exactly the tab-strip problem Phase 2.3 asks to replace.
- The Overview page's KPI row + "what's happening at each stage" list —
  functional but not an editorial opening sequence; no scrollytelling, no
  guided question-answer structure per Phase 6.

## Major technical risks for the overhaul

1. **No-JS / static-fallback requirement vs. pure client-rendered SPA** —
   the single biggest structural gap. Needs a real decision (see
   accompanying message) before Phase 5/11 work can be considered done.
2. **Chart library adoption is repo-wide**, not additive — introducing one
   touches every existing chart component.
3. **Zero test coverage today** — Phase 13's testing requirements start
   from nothing, not from a partial suite.
4. **134 real chart instances across 86 exhibits** (some exhibits render
   as 2-3 chart instances, e.g. multi-part CSVs) all need an individual
   Phase 1 disposition — this is a large, unavoidably manual classification
   task, not something to automate away.
5. **No existing component gallery/Storybook** — Phase 3.4 asks for one;
   none of this app's 15 components have documented props/variants outside
   their own source comments.
